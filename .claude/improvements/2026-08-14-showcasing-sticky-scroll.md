## Цель

Секция Showcasing на главной перестаёт быть таймер-каруселью (Swiper, автоплей каждые 3с, ручная пауза, полоса прогресса) и становится **скролл-driven липкой витриной**: секция «прилипает» (`position: sticky`) на весь экран, и смена проекта происходит по мере прокрутки страницы пользователем — скорость и направление задаёт сам пользователь, а не таймер.

Это единственный оставшийся в плане анимаций приём верхнего эшелона («самый сильный визуально» по формулировке плана). Все остальные пункты плана закрыты.

## Почему делаем именно так (решено в обсуждении 2026-08-14)

- **Не полоса прогресса, а точки-индикатор.** Полоса прогресса физически бессмысленна без таймера — заменяется на 4 точки (по числу проектов), подсвечивающие активный экран.
- **Кнопка паузы не нужна вообще**, а не переезжает в новый вид. Анимация не идёт без действия пользователя (сам скролл — это и есть управление), поэтому требование WCAG 2.2.2 (Pause, Stop, Hide), из-за которого кнопка появилась в Swiper-версии, здесь не применяется по конструкции, а не гасится костылём.
- **Ссылка на карточку и hover/focus-подсказка «Смотреть проект» переносятся без изменений** — это прямое требование §6 плана: «любая переделка Showcasing обязана сохранить их, иначе заново открывает эту же дыру» (баг «с карточки нельзя дойти до проекта», закрытый 2026-08-14).

## Механика (проверена в демо, переносится в React+CSS)

1. Секция превращается в высокую обёртку — высота ≈ `N карточек × 100vh` (в демо ровно `400vh` на 4 карточки; точный множитель — предмет тонкой настройки на реализации, может быть меньше 100vh на карточку для более быстрого темпа).
2. Внутри — `position: sticky; top: 0; height: 100vh` вьюпорт, который держит текущую карточку неподвижной, пока пользователь скроллит родительскую высокую обёртку.
3. Прогресс прокрутки через эту обёртку пересчитывается в «непрерывный индекс» (0…N), который управляет:
   - `opacity` каждой карточки (кроссфейд с нахлёстом ~15% на границах — та же кривая, что в демо-скрипте);
   - активной точкой в индексе сбоку;
   - счётчиком «01 / 04».
4. Реализация — на **чистом скролл-слушателе** (`requestAnimationFrame`-throttled), как в демо, а не на CSS `animation-timeline: view()`. Причина: здесь таймлайн общий на всю секцию и должен управлять несколькими независимыми свойствами (4 карточки + 4 точки + счётчик) синхронно — JS-подход проще держать в одном месте правды, чем размазывать по `animation-range` на каждый элемент. (В About-подсветке фраз, наоборот, CSS scroll-timeline был правильным выбором — там один элемент, один эффект.)

## Что демо **не** показывает и обязательно нужно добавить в реализации

1. **Клавиатурный фокус на невидимой карточке.** Если все 4 карточки лежат в DOM и скрыты через `opacity`, `Tab` может увести фокус на карточку вне текущего окна прокрутки — фокус есть, а на экране её не видно. Нужно: `focus` на ссылке карточки → `scrollIntoView`/`scrollTo` к её сегменту (в демо есть заготовка `segmentTop(i)` для клика по точке-индикатору — переиспользовать ту же функцию для фокуса).
2. **Фолбэк без scroll-driven механики.** Для `prefers-reduced-motion: reduce` и для случая, когда решим не гейтить обычным `@supports` (сам sticky не требует новых CSS-фич, а вот плавность кроссфейда — решение желательное, не строго обязательное) — простая раскладка: 4 карточки друг под другом в обычном потоке документа, без `position: sticky`, без JS-пересчёта. Это тот же паттерн деградации, что и в §2 плана анимаций («нет поддержки → страница ровно такая, как сейчас, она уже работает»).
3. **Открытый вопрос по layout, не решённый в демо:** в демо контент карточки на всю ширину вьюпорта (edge-to-edge). На реальном сайте `.showcasing__wrapper` градиентный фон уже сейчас полноширинный, а сам контент карусели живёт внутри `.container` (максимум 1440px). Предлагаю: фон — на всю ширину (как сейчас), содержимое карточки — по центру в разумных пределах ширины (не растягивать текст на весь 1920px экран) — но финальные отступы/ширину нужно проверить на реальном макете, не додумывать заранее.

## Верификация при реализации

```
npm run lint
npm run test:run   # 14/14
npm run build
```

- Playwright: desktop 1440, tablet 900/768, mobile 390 — прокрутка мышью/колесом действительно листает карточки, без рывков.
- Клавиатура: `Tab` до каждой карточки — видимая карточка должна совпадать с сфокусированной (после доработки из пункта 1 выше).
- `prefers-reduced-motion: reduce` — фолбэк-раскладка проверяется отдельно (Playwright `emulateMedia`), как в фиксах этой же сессии для `socials`/`Testimonials`.
- Ссылка `/projects#project-{id}` с каждой карточки по-прежнему работает (тот же тест, что проверял §6 при первой реализации — `ScrollToTop` докручивает до нужной карточки на `/projects`).
- Итоговый скролл-хайт секции не должен ломать общую навигацию по странице (якорные ссылки в шапке на другие секции, если такие есть).
