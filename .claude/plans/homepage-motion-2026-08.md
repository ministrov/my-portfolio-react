## 1. Развилка по инструменту — решена

Есть два разных механизма, которые постоянно путают:

|                      | Что делает                                         | Ощущение            |
| -------------------- | -------------------------------------------------- | ------------------- |
| **Scroll-triggered** | Элемент попал в кадр → проиграть анимацию один раз | «что-то проявилось» |
| **Scroll-linked**    | Позиция анимации **и есть** позиция скролла        | «страница живая»    |

Всё, что было на сайте раньше, — первое. Поэтому оно и ощущалось
шаблоном: анимация не связана с пользователем, она выстреливает по
таймеру. Вторая реагирует непрерывно, в обе стороны, со скоростью
пользователя.

### Граница между системами

Чтобы в проекте не оказалось двух конкурирующих систем движения:

- **CSS scroll-timelines** (`animation-timeline: view()`) — всё
  непрерывное, привязанное к скроллу. Считается вне основного потока,
  ноль JS, ложится в конвенцию проекта «обычный CSS + BEM».
- **`motion`** — остаётся там, где движение дискретное и по действию:
  аккордеон FAQ (`AccordionPanel`), форма↔успех и inline-ошибки
  (`ContactForm`), `AnimatePresence`, `useInView` для гейтов автоплея.

Не смешивать: если приём непрерывный — это CSS; если он про смену
состояния — это `motion`.

### БЛОКЕР: сейчас `view()` в этом проекте не работает вообще

Проверено эмпирически (Chrome 151, 2026-08-14), не по документации.

`src/styles/main.css` объявляет `body { overflow-x: hidden }`. При
`overflow-x: hidden` вычисленный `overflow-y` становится `auto`, то есть
**`body` — скролл-контейнер**. `view()` резолвится относительно
ближайшего скролл-контейнера-предка, а `body` сам не прокручивается
(прокручивается документ). Итог: таймлайн замирает на прогрессе 0.

Замер: элемент с `animation-range: exit` держал `opacity: 1` на всех
позициях скролла (0 / 0.25 / 0.5 / 0.75 / 1 высоты секции).

Коварство в том, что `@supports (animation-timeline: view())` при этом
возвращает **true**. Фолбэк из §2.2 не срабатывает: правило применяется,
анимация «есть», но её прогресс всегда 0. Поэтому §2.1 (никаких
`opacity: 0` в базовом состоянии) — не про старые браузеры, а про этот
самый режим: с `from { opacity: 0 }` контент исчез бы навсегда.

**Исправление:** `body { overflow-x: clip }` вместо `hidden`. `clip` не
создаёт скролл-контейнер, горизонтальное обрезание сохраняется. Проверено
там же: после замены прогресс пошёл. У `html` уже стоит `overflow-x: clip`
— правило на `body` дублирующее, менять его безопасно.

Это **предусловие для любого шага** ниже. Пока оно не сделано, каждый
CSS-приём из этого плана будет молча ничего не делать.

### Вторая ловушка: `.hero { overflow: hidden }`

По той же причине `.hero` — собственный скролл-контейнер, поэтому
`animation-timeline: view()` на `.hero__inner` (буквально то, что написано
в шаге 2) не заработает даже после исправления `body`.

Замер трёх вариантов в середине `exit`:

| Вариант                                        | opacity  | сдвиг    |
| ---------------------------------------------- | -------- | -------- |
| `view()` внутри `overflow: hidden`             | `1`      | `0`      |
| `view-timeline-name` на самой `.hero` + ссылка | `0.52`   | `-40px`  |
| `view()` без `overflow: hidden`                | сработал | сработал |

Рабочая форма — именованный таймлайн на секции, а не `view()` на потомке:

```css
.hero {
  view-timeline-name: --hero;
}
.hero__inner {
  animation-timeline: --hero;
  animation-range: exit;
}
```

Имя видно потомкам без `timeline-scope`. Снимать `overflow: hidden` с
`.hero` не нужно.

## 2. Контракт на всё новое

Версии браузеров в плане намеренно не указаны — поддержка проверяется
конструкцией, а не таблицей:

1. **Контент читаем в состоянии по умолчанию, всегда.** Анимация только
   меняет то, что уже видно. Никаких `opacity: 0` в базовом состоянии.
2. Всё новое живёт внутри `@supports (animation-timeline: view())`.
3. Нет поддержки → страница ровно такая, как сейчас. Она уже работает.
4. `prefers-reduced-motion` — на каждом приёме, без исключений.

Каркас правила:

```css
@supports (animation-timeline: view()) {
  @media (prefers-reduced-motion: no-preference) {
    .selector {
      animation: name linear both;
      animation-timeline: view();
      animation-range: entry 40% cover 55%;
    }
  }
}
```

## 3. Распределение по секциям

Правило владельца — «через одну секцию» — берётся как жёсткое:
**один приём на секцию, соседние секции не повторяются, часть секций
намеренно неподвижна.**

Таблица ниже — в редакции 2026-08-14 (см. ревизию в §4).

| Секция           | Приём                                                   | Почему                                                  |
| ---------------- | ------------------------------------------------------- | ------------------------------------------------------- |
| **Hero**         | **Ничего не добавлять**                                 | Фокусный момент уже занят: скрамбл + блик + рамка CTA   |
| **About**        | Подсветка фраз по скроллу + расшифровка цифр статистики | Чинит недостижимый на тач приём; несёт подпись проекта  |
| **Showcasing**   | **Ничего не добавлять**                                 | Карусель движется сама, прогресс и ссылка на месте      |
| **Services**     | **Ничего не добавлять**                                 | Отклик на иконке уже есть                               |
| **Advantages**   | **Ничего не добавлять**                                 | Это бенто-сетка, а не список — стаггер читался бы шумом |
| **Testimonials** | **Ничего не добавлять**                                 | Автопрокрутка + прогресс                                |
| **FAQ**          | **Ничего не добавлять**                                 | Аккордеон и есть движение                               |
| **Contact**      | **Ничего не добавлять**                                 | Состояния формы и есть движение                         |

Правило «через одну секцию» сохраняется, но читается точнее: **нельзя
повторять один и тот же приём на соседних секциях**. Два приёма внутри
About его не нарушают — это разные регистры в разных блоках, разнесённые
почти на экран прокрутки: непрерывная обратная связь на чтении абзаца и
разовая расшифровка на строке фактов.

Ритм: громко (hero) → живое (About) → самодвижущееся → покой → покой →
самодвижущееся → покой → покой.

### Шаг 1 — About: подсветка ключевых фраз по скроллу — ДЕЛАТЬ (первым)

**Файл:** `src/components/aboutStory/style.css`

Сейчас `.about-story__mark` имеет `background-size: 100% 0.32em` в покое
и растёт до `100% 92%` по `.about-story__para:hover`. То есть **на
телефоне приём не срабатывает никогда**, а при обычном чтении со скроллом

Сделать: та же геометрия и те же цвета, но `background-size` растёт по
мере прохождения абзаца через экран. Hover-версию оставить для мыши.

### Шаг 2 — Hero: параллакс-уход — НЕ ДЕЛАТЬ

**Причина 1, содержательная.** У hero **уже есть** авторский фокусный
момент, и он же — подпись всего сайта (DESIGN.md → Signature: The
Developer's Console): расшифровка подзаголовка, разовый блик по
заголовку, вращающаяся радужная рамка CTA. Параллакс не добавляет к нему
смысла, а конкурирует с ним за тот же жест — первую прокрутку. На секцию
приходится один фокусный момент, и он занят.

**Причина 2, техническая.** `.hero { overflow: hidden }` делает секцию
собственным скролл-контейнером, поэтому запись из этого шага
(`view()` на `.hero__inner`) не работает — замер в §1. Обходится
именованным таймлайном, но обходить нечего: приём не нужен.

**Причина 3.** Параллакс — общее место, а не решение этого продукта.

### Шаг 3 — Advantages: разноскоростной подъём — НЕ ДЕЛАТЬ

Шаг опирается на утверждение §3 «единственное место, где список честно
читается как список». **Это неверно.** `.advantages__list` — бенто-сетка
с вручную расставленными позициями: карточка 1 занимает 2×2, карточки 2 и
3 — по 2×1 справа от неё, 4 и 5 — по 1×1, 6 — 2×2, 7 — 1×2.

Отсюда два следствия:

- Порядок в DOM ≠ порядок чтения. Карточки 2 и 3 стоят одна под другой в
  правой колонке; смещение по `:nth-child()` развело бы их по скорости
  без всякой причины. Карточки 4–7 занимают одну визуальную полосу —
  смещение по индексу читалось бы как дрожание, а не как ритм.
- Сеткой это остаётся только шире 1024px. На `≤1024px` — 2 колонки с
  авторазмещением, на `≤768px` — одна колонка. То есть «список» здесь
  существует ровно там, где бенто-иерархия уже развалилась.

Можно было бы ограничить приём диапазоном `≤1024px`, но тогда это просто
поочерёдное появление карточек в столбик — то самое, что сняли в
`15d7975`. Убрать его — ничего не потеряется. Значит, это украшение.

Advantages остаётся неподвижной. Отклик на hover у карточек уже есть.

### Шаг 4 — Цифры About как показания консоли — ДЕЛАТЬ (фокусный момент)

**Файл:** `src/sections/about/About.jsx`

`4+ / 10+ / Middle / B2` (`ABOUT_STATS` в `src/const/index.jsx`)
набираются, когда блок проходит через экран.

Это **главный приём плана**, а не самый дорогой шаг в конце. Он
единственный воплощает выбранный мир проекта: делает плашки показаниями
консоли, а не просто числами, и снимает одиночество скрамбла — подпись
перестаёт быть разовым трюком в hero и становится системой.

**Упрощение, которое план не заметил:** отдельный хук не нужен.
`hooks/useScrambleText.jsx` уже делает ровно посимвольную расшифровку

- Забота «`Middle` и `B2` — не числа» снимается сама: скрамбл работает с

- Приём получается не похожим на подпись, а **буквально тем же

- Гейт `active` у хука уже есть (в hero — `isSubtitleInView`); здесь

Ограничения: `loop` **не включать** — в hero он согласован с владельцем
отдельно, здесь цикл превратил бы факты в мигающую вывеску. Один проход
на вход в кадр. `prefers-reduced-motion` — сразу финальные значения.
Разметка должна отдавать финальный текст скринридеру (в hero это уже
решено парой `visually-hidden` + `aria-hidden`), иначе цифры уедут из
доступного дерева.

Учесть: как и шаг 1, меняет и `/about`.

## 6. Открытый вопрос вне анимации — РЕШЁН 2026-08-14

Было: `ShowcasingCard` (карусель на главной) не содержал ни одной ссылки
и не был кликабелен. С главной страницы дойти до проекта было нельзя —
карточка показывала картинку и название, и всё.

Решение: вся карточка — растянутый `<Link>` на `/projects#project-{id}`,
то есть на карточку этого же проекта на странице проектов (а не сразу на
внешний `demoLink`: питч — обзор, стек, год, роль — читается до ухода с
сайта, и проект `mish` без `demoLink` не выпадает). Ссылку сопровождает
подсказка «Смотреть проект» на hover/focus и cobalt-тень на фото —
приём тот же, что уже несёт `ProjectCard`.

Коммиты:

- `13d8b81 feat(projects): let project cards be a scroll-to anchor target`
- `5b318c1 feat(showcasing): make carousel cards link to their project`

По ходу вскрылись и закрыты три вещи, без которых ссылка не работала бы:

- `useUrlParams` пересобирал URL из `pathname + search` и **терял hash** на
  каждой синхронизации `?lang=`.
- В fade-эффекте Swiper неактивные слайды остаются в DOM с `opacity: 0` —
  их ссылки перехватывали бы клики и Tab у видимой карточки
  (`visibility: hidden` по `:not(.swiper-slide-active)`).
- Первый скролл к якорю сбивался: `font-display: swap` и entrance-анимация
  `ProjectsList` двигают лейаут уже после него. `ScrollToTop` теперь
  досводит прокрутку по кадрам, пока позиция цели не перестанет плыть, и
  сразу уступает, если пользователь сам скроллит/тапает/жмёт клавишу.

**Последствие для §5 (липкая витрина):** карточка витрины теперь несёт
ссылку и hover/focus-подсказку. Любая переделка Showcasing обязана их
сохранить — иначе она заново открывает эту же дыру.

**Последствие для §4 (шаг 3, Advantages):** entrance-анимация,
двигающая лейаут, ломает якорную прокрутку. `ScrollToTop` это уже терпит,
но новые приёмы лучше строить так, чтобы они **не меняли высоту потока** —
`transform`/`opacity`, а не `margin`/`height`. Это же требование §2.1.
